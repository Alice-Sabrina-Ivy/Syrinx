# Phone check of the main-thread pass, and the trace redraw cadence — 2026-10-12

Branch `trace-raf60` (from `cue-strip` 1366c39). Public data only: the phone
heard public LibriSpeech test-clean speech played from the PC speakers; the
desktop runs play the LibriSpeech smoke WAVs through Chrome's fake microphone.
Follows [main-thread-cpu-2026-10-08.md](main-thread-cpu-2026-10-08.md), whose
§3.1 left the phone unmeasured and kept the review's display-rate redraw loop
(capped at ~60 Hz) as a phone-check variant.

**Outcome.** On the phone the current `cue-strip` head uses 30 % (panel off) /
34 % (panel on) less main-thread CPU than the base before the main-thread pass.
Its data-driven trace redraw (one draw per 40 ms audio buffer, ~25 draws/s)
scrolls smoothly by the automated screen-recording check but fails guard 3c's
gap bar (p99 52 ms against 50 ms). The variant — an animation-frame loop that
draws at most every 16 ms while data is arriving — draws ~53 times a second
(gap p99 34 ms, guard 3c passes) and also scrolls smoothly, at **+27 % (panel
off) / +30 % (panel on) main-thread CPU** against the head; still 11 % / 14 %
below the base. **User decision (2026-10-12): ship the smoother variant,
accepting that CPU cost.** This branch brings it into
`src/components/traceRedrawScheduler.js` (§4). On the desktop (§5.1, headless
Chrome at ~180 frames/s) the change costs **+52 to +58 % main thread** (in
ms/s load-dependent: +60 to +63 on a loaded machine, +28 to +31 in a
quieter-machine review repeat), and a new point reaches the screen ~6–9 ms
later (phone: ~1 ms); trace pixels at data steps and the cue strip are
unchanged. The loop draws on most, not every, 60 Hz frame (§4: callback
jitter against its 16 ms gate). **§7 (branch `trace-vsync`, phone-checked
2026-10-19, §7.6: PASS 6 / 6, merged into `cue-strip`):** gating on the frame
timestamp instead draws on every 60 Hz frame — on the phone 60.0 draws /s for
women and men (a9ddd6b 52.3), frame-timestamp gap p99 16.8 ms, draw-end gap
p99 20.9 ms (a9ddd6b 33.5), SMOOTH by the automated screen-recording check;
on the desktop at ~180 Hz it measures the same as a9ddd6b (draws /s, CPU and
latency within run spread; frame-timestamp gap p99 16.8–16.9 ms in 8 / 8
runs, §7.5). Phone main-thread cost: +10.5 ms/s (+3.1 %) in the one usable
(diag) pair; the production pair was spoiled by the phone locking, so the
production-page cost is unmeasured (§7.6). The phone pass condition on gaps
was restated before any phone data (§7.3 amendment): it judges
frame-timestamp gaps, since draw-end gaps keep the callback jitter.

## 1. Method

### 1.1 Device and harness

- **Phone**: Pixel 11 Pro XL (Tensor G6, Android 17, build
  CD1A.260905.001.B1), Chrome 154.0.8037.127, **portrait**, auto-rotate off,
  Do Not Disturb on, "Stay awake while charging" on, USB-powered. Capture path
  MSTP at 48 kHz; the hardware delivers audio in **40 ms frames** (the desktop
  delivers 25 ms chunks), so the hook appends one or two trace points per
  hardware frame. Thermal status 0 at the start of every run (skin 27.5 °C at
  the first run, 32.9 °C at the last).
- **Harness** (scratch only, not committed): the pattern of
  `scripts/mobile-diag-capture.js` — `adb` + a CDP forward to the phone's
  Chrome tab, the build served by `vite preview` on the PC and reached with
  `adb reverse`. It kills only the PIDs it spawned (preview server, audio
  player, its own `screenrecord`) and removes only its own forward / reverse.
- **Audio**: a public LibriSpeech test-clean loop, 5 women and 5 men in
  alternating blocks of ~30 s, played through the PC speakers next to the
  phone, at the volume of the 2026-10-07 phone session.
- **Run** (each build): direction question answered, Start Listening, 15 s
  warm-up, a **60 s panel-off stage**, the experimental "Likely heard as" panel
  switched on (model ready), 15 s warm-up, a **60 s panel-on stage**, panel off
  again. ~3.5 min per run plus a 30 s rest.
- **CPU figures** (ms of CPU per wall-clock second):
  - **main /proc** — CPU ticks of the renderer's `CrRendererMain` thread from
    the phone's `/proc`;
  - **TaskDuration** — CDP `Performance.getMetrics` TaskDuration of the page's
    main thread;
  - **workers /proc** — the sum over all `DedicatedWorker` threads (Chrome
    names every worker thread the same, so they cannot be split by name);
  - **all Chrome** — every Chrome process on the phone (browser, renderer,
    GPU, utility).
  CPU numbers come from the production page (no `?diag=1`): the diag overlay
  costs ~45–60 ms/s of main thread on the phone. The `?diag=1` runs give the
  trace cadence, latencies, the resonance worker and the gender worker.
- **Women and men**: whole-stage `/proc` CPU covers equal shares of women's and
  men's speech and cannot be split. Every diag metric is split per voice: each
  5 s interval is labelled by its median voiced F0 (≥ 165 Hz women, ≤ 140 Hz
  men) and intervals spanning a block change are dropped.

### 1.4 Smoothness from a screen recording (automated, rule fixed in advance)

The by-eye judder check was replaced on 2026-10-11 by an automated check whose
rule was written before any capture was analysed (scratch `phone-smooth/RULE.md`;
analyser `analyze.py`). During the panel-off stage of HD and VD,
`adb shell screenrecord` records the phone's real composited screen for 60 s
(1344 × 2992, variable frame rate, presentation timestamps); it is pulled to
the PC and deleted from the phone. The analyser locates the trace plot from the
page's DOM rect and a CDP screenshot (template match on the y-axis labels),
removes the static layer, registers each frame by horizontal sub-pixel shift
and measures the scroll. On `?diag=1` the overlay covers the right of the plot,
so the uncovered left strip is used (the whole trace scrolls as one). A
visible change is ≥ 0.1 CSS px.

**JERKY** if any of: J1 median update interval > 50 ms (< 20 updates/s);
J2 > 3 hitches (pauses > 100 ms) per minute; J3 longest pause > 250 ms;
J4 > 2 % jumps (steps > max(2 × median, 1 CSS px)); J5 > 0.5 % backward steps;
J6 step-size CV > 0.6. INCONCLUSIVE if < 20 s is analysable or the plot is not
found. Amendments after validation touch instrument validity only (J4 / J6 are
assessed only when the capture runs ≥ 1.5 × the update rate and, with a diag
draw record, shows ≥ 95 % of the page's draws; a slow capture can turn a smooth
trace jerky but never the reverse, so only a would-be JERKY result becomes
INCONCLUSIVE). Validated on the desktop before the session: H and V SMOOTH at
25 ms and at 40 ms data cadence; traces held to 8 and 12 Hz and a trace with
150–300 ms stalls every 1.5–3.5 s all JERKY.

## 4. Decision and change

**Adopted: V** (user decision 2026-10-12) — the smoother trace (52.7 vs 25.4
updates/s, guard 3c passing on the phone), accepting **~+27 % (panel off) /
+30 % (panel on) main-thread CPU on the phone vs H** (+68 / +72 ms/s; +15 %
over all Chrome processes). This reverses §3 F1 of the main-thread note, which
had kept the data-driven cadence to save that per-frame work before the phone
could judge it.

The scheduler in `src/components/traceRedrawScheduler.js` becomes the
variant's logic unchanged (f7032b9's diff from c925457): while data is
arriving (a notification within the last `IDLE_AFTER_MS` = 1 s) an
animation-frame loop draws when at least `MIN_DRAW_MS` = 16 ms have passed
since its last draw; once data has stopped for 1 s it draws on a 100 ms
timeout (`IDLE_FALLBACK_MS`), as before. The 16 ms gate reads
`performance.now()` inside the frame callback, and a 60 Hz frame is 16.67 ms,
so it has 0.67 ms of slack: with a jitter-free clock the loop draws every
frame at 60 Hz and every other frame at 120 Hz, but when one callback runs
late the next frame measures < 16 ms and draws nothing, doubling that gap.
**That is why the phone drew ~53 /s, not 60** (VD `traceDraws`: 87.5 % of
gaps at one 60 Hz frame, 12.5 % at two, 28–36 ms; no 25 ms gaps, so the
page's frames came at 60 Hz intervals there; the one-frame gap just before a
skip averages 18.1 ms against 16.7 ms before a normal one), and why its gap
p99 is 34 ms. In the unit test's jittered model (`now()` = vsync + U[0, J])
the loop draws 57.4 / 46.8 / 42.0 /s at J = 1 / 2 / 4 ms on a 60 Hz display
and 53.1 /s at 2 ms on 120 Hz; a 90 Hz display draws every other frame
(45 /s), 144 Hz every third (48 /s). Stall safety: a feed that stalls while
listening keeps the loop running, so no freeze exceeds 16 ms + J + one frame
(60 Hz: two frames, 33 ms; 120 Hz with J = 2 ms: 25 ms) — inside the
2026-10-08 review fix's bound of 50 ms plus a frame, which the unit test
keeps as its guard (`STALL_BOUND_MS`, now a test constant: no code path
schedules a 50 ms timeout). A burst of notifications still draws once; a
hidden page keeps at most one pending frame; `stop()` cancels the frame and
the timer.

**Historical (superseded 2026-10-12, §7, branch `trace-vsync`):** Not
adopted: gating on the frame timestamp (the `requestAnimationFrame`
argument, the same for every callback in a frame) instead of
`performance.now()`. It would draw every 60 Hz frame (~60 /s on the phone,
+14 % draws over what the user priced on 2026-10-12), so it needs a phone
re-measure or an explicit user decision first. — `trace-vsync` builds it (§7);
it merges only after the §7.3 phone check (as amended). **Outcome
(2026-10-19, §7.6):** the phone check passed (6 / 6: 60.0 draws /s, frame-timestamp
gap p99 16.8 ms, SMOOTH), and `trace-vsync` merged into `cue-strip`; the
frame-timestamp gate replaces the `performance.now()` gate described above.

machine stalls: the head woman run had 3 main-thread tasks > 50 ms). **New
finding — latency:** on the desktop the trace now shows a new point ~6–7 ms
later than before (draw − readout +5.9 / +7.5 ms, women / men). The data-driven
redraw drew on the first frame after each point; the loop draws only when
≥ 16 ms have passed since its last draw, a phase not tied to the data, so a
point waits on average about half a draw period (the quieter-machine review
repeat, men: draw − readout 3.0 → 11.6 ms, capture → painted 5.9 → 13.0 ms).
On the phone the difference is ~1 ms (§3: draw − readout H 8.8 / 8.7 → V 9.6 / 10.0 ms, capture → painted
20.0 / 20.4 → 21.4 / 21.6 ms, panel off / on), where the 40 ms buffers already
set the phase. It exceeds the main-thread note's guard 1 bar (+5 ms) on the
desktop; reported, not judged — the decision was made on smoothness.
Possible follow-ups (not built; each needs a draw-rate check, and a phone
re-measure or user decision, before adoption): (1) gate on the frame
timestamp (§4), which removes the jitter skips and with them most of the
extra lag on a 60 Hz display, where a loop that draws every frame shows a new
point on the next frame, like the data-driven redraw; (2) re-phase the loop
on each notification: draw if at least ~`MIN_DRAW_MS` / 2 has passed since
the last draw and restart the 16 ms phase from there, which keeps at most
about one extra draw per data point. Not proposed: an uncapped draw on the
first frame after every notification, which on 120–180 Hz displays with a
40 Hz feed allows ~100 draws/s and brings back much of the per-frame cost the
cap limits. On 120 Hz and faster displays a wait of about half a draw period
is inherent to a 16 ms phase that ignores the data.

## 6. What remains unmeasured

- **Mid-range and older phones**: one flagship (Tensor G6) only. On a slower
  phone the per-frame cost is a larger share of the main thread, and the
  phone's display rate (60 vs 90 / 120 Hz) sets how often the loop wakes.
- **Landscape** on the phone: this session was portrait (the 2026-10-07
  session was landscape; not comparable).
- **Safari / iOS** and **Firefox** (the AudioContext fallback path, 25 ms
  chunks): not measured; the scheduler only uses `requestAnimationFrame` and
  `setTimeout`.
- **Repeat runs on the phone**: one run per build; the phone's run-to-run
  spread and a second B / H pair are not measured. The split of H vs B into
  the main-thread pass vs the Clarity row + CPP retirement (the optional split

## 7. Drawing on every frame: gate on the frame timestamp (branch `trace-vsync`, pre-registered)

Branch `trace-vsync` from `cue-strip` a9ddd6b. Built to answer the user's
question how much better drawing on every frame would be (§4's "Not adopted"
option, §5.1 follow-up 1). **Not adopted by this section**: a candidate whose
merge waits for the phone check in §7.3. **Outcome (2026-10-19):** the phone
check passed 6 / 6 (§7.6) and the branch merged into `cue-strip`.

### 7.1 Mechanism (why a9ddd6b draws ~53 /s, not 60)

a9ddd6b's loop draws when `performance.now()` inside the frame callback is
≥ `MIN_DRAW_MS` (16 ms) past the previous draw's `performance.now()`. A 60 Hz
frame is 16.67 ms, so the gate has 0.67 ms of slack against callback jitter:
when callback k runs J ms after its frame and callback k + 1 runs on time, the
second measures 16.67 − J ms and skips if J > 0.67 ms, doubling that gap to
33 ms. On the phone 12.5 % of gaps were doubled (§3.1, §4: ~53 draws /s, gap
p99 34 ms; the one-frame gap measured just before a skip averages 18.1 ms
against 16.7 ms before a normal one, i.e. the previous callback ran late).

The `requestAnimationFrame` callback's argument is the frame's timestamp: the
same value for every callback in that frame, tied to the display frame rather
than to when the callback ran. Gating on it removes the callback jitter from
the comparison. A headless-desktop probe (Chrome 154, scratch only) measured
frame-timestamp intervals of 5.3–5.8 ms at ~176 frames /s (median 5.6;
timestamps coarsened to 0.1 ms, the page is not cross-origin isolated) while
`performance.now()` inside the callback ran 0.1–3.5 ms after the timestamp
(median 0.3, p99 0.5).

### 7.2 The change

`traceRedrawScheduler.js` gates on the frame timestamp passed to the callback
(falling back to `now()` if none is passed) with a tolerance:
draw when `ts − lastDrawTs ≥ MIN_DRAW_MS − DRAW_TOLERANCE_MS` = 16 − 1 = 15 ms.
Why 15 ms:

- **60 Hz never skips**: a frame interval of 16.67 ms clears 15 ms with
  1.67 ms of margin for frame-timestamp irregularity (the 0.1 ms coarsening,
  any platform vsync-time noise). Callback lateness no longer matters.
- **Faster displays stay near 60 /s**: draws /s = R / k with k the smallest
  number of R Hz frames spanning ≥ 15 ms: 120 Hz every other frame (60 /s),
  144 Hz every third (48 /s; two frames are 13.9 ms), 165 Hz every third
  (55 /s), 180 Hz every third (60 /s), 240 Hz every fourth (60 /s). The
  absolute ceiling for any display is 1000 / 15 = 66.7 draws /s.
- **Unchanged from a9ddd6b**: 90 Hz every other frame (45 /s), 144 Hz 48 /s,
  75 Hz every other frame (37.5 /s — one 75 Hz frame is 13.3 ms; drawing every
  frame there would need a gate ≤ 13.3 ms, which would put 144 Hz displays at
  72 /s; not chosen).
- A lower tolerance (gate 15.5–16 ms) would leave 60 Hz ≤ 0.67–1.17 ms of
  margin; a higher one (gate ≤ 13.9 ms) lets 144 Hz draw every other frame.
- Two refresh-rate ranges put a whole number of frames within timestamp noise
  of 15 ms, so the cadence may switch irregularly between k and k + 1
  frames there: ~64–67 Hz (one frame 15.0–15.6 ms) and ~133–137 Hz (two
  frames 14.6–15.0 ms). No common display runs at those rates.

Kept: the idle cadence (`IDLE_AFTER_MS` 1 s after the last notification, then
a draw every `IDLE_FALLBACK_MS` 100 ms), one pending frame at most, `stop()`.
Stall bound: a stalled feed keeps the loop running; with exact frame
timestamps no gap exceeds 15 ms + one frame (60 Hz: one frame; 120 Hz: two;
144 / 180 Hz: three), and dropped display frames (a busy main thread) no
longer add a skipped frame on top, because the next frame's timestamp is
already ≥ 15 ms on.

Expected effect: on a 60 Hz display (the phone's page frames, §4; most desktop
monitors) a draw on every frame — ~60 draws /s instead of ~53, gap p99 one
frame (~17 ms) instead of 34 ms, and a new point on the next frame after it
arrives (§5.1: the extra desktop draw-readout lag came from the 16 ms phase,
which every-frame drawing removes on a 60 Hz display). CPU: ~+14 % draws
over a9ddd6b on the phone. An upper bound from §2 (V − H: +67.6 ms/s main
thread `/proc`, +152.7 ms/s all Chrome, for +27.4 draws /s, i.e. ≤ 2.5 /
5.6 ms per draw including the loop's wakes) puts +7 draws /s at ≤ +18 ms/s
main thread (≤ +6 % over a9ddd6b's ~320 ms/s) and ≤ +40 ms/s over all
Chrome processes (≤ +3 %). On headless desktop Chrome (~176–180 frames /s)
both versions draw on every third or fourth frame; the change is expected to
be small there (a9ddd6b measured 57–59 draws /s in §5.1; expected ~58–60).
